A fee discount is not a reason to add volume. If the proposed transaction does not otherwise fit your plan, the presence of an invitation does not improve its market risk or justify making it. The volume boundary is a limit on a benefit, not a target to reach.

## What a builder fee means

Hyperliquid's [builder-code documentation](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/builder-codes) describes an additional fee that an application can attach to orders it submits for a user. The user approves a maximum fee for a specific builder, and that permission can be revoked. Builder charges are set per order, so approving a ceiling does not establish what every future order will cost.

This makes the approval screen meaningful. Read the builder identity, maximum rate and relevant account before approving anything. A well-known interface name and an unfamiliar address may still require clarification; identify the relationship through the application's official information. Do not infer the purpose of a wallet request from the referral code alone.

The approval is also not an instruction to use the maximum. If an interface has permission to charge up to a certain rate, ask what it proposes to charge for the particular order. A ceiling protects against one kind of surprise, but the actual quotation remains necessary for a useful comparison.

## Compare the same cost components

A practical comparison uses the same proposed position size, market, order type and observation time. First note the trading-fee estimate. Then identify any builder charge separately. Also consider execution price and other applicable costs; an interface with a lower visible charge can still deliver a different execution outcome.

Suppose, purely as an illustration, that an eligible base trading fee is 20 units. A 4% reduction of that component saves 0.80 units. If a separate interface charge is 3 units and is not discounted in this hypothetical model, the combined amount would be 22.20 units. The calculation does not establish the treatment of any actual builder charge. It shows why applying 4% to an entire screen total without identifying the components can be misleading.

Ask the interface which fee base receives the referral benefit and whether its quotation already includes that benefit. Otherwise, you could subtract the same discount twice when estimating the final amount. Compare a clearly defined total with another clearly defined total, rather than one interface's partial number with another interface's complete number.

## Keep approvals and trade records separate

An approval record describes what an application was permitted to request. A fill record describes what happened on an executed order. Retain both when investigating a discrepancy, along with the market, time, quantity, referral status and displayed estimate. A screenshot of only the approval ceiling cannot explain the actual fee on a fill.

If several fills complete one order, compare the relevant fills rather than assuming the first entry represents the entire transaction. Avoid combining unrelated orders into a single fee percentage before understanding their treatment. This is ordinary recordkeeping, not a recommendation to submit a test trade.

## Questions worth resolving in advance

**Does PERPLIST remove an application's builder fee?**

The standard referral terms do not establish that promise. Check the actual interface's quotation and current documentation instead of treating every charge as the same fee.

**Does the main wallet's discount automatically cover a vault?**

No. The official referral page expressly excludes vaults and subaccounts from the discount.

**Is a maximum builder-fee approval the quoted price of an order?**

No. It is an authorization ceiling. The order-specific charge still needs to be understood.

**What happens after the referral volume allowance is used?**

The documented referral discount is limited to the first $25 million of volume. Read the current fee terms and account display rather than assuming it continues indefinitely.
